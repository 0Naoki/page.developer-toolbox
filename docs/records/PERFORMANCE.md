2026年11月9日の2件（`performance-2026-11-09-before.json`・`performance-2026-11-09-after.json`）は、終了状態（`outcome`）とビルドのハッシュ（`build`）を記録する前のスクリプトで測りました。記録には終了状態がないため、対象コミット `4e4613e` の上限から終了状態を判断しました。結果ではなく上限エラーの表示までの時間なのは、正規表現の10,000行・100,000行（テスト文字列の上限10万単位を超える）と、証明書の100,000行（入力の長さの上限を超える）です。これらの値は、入力欄の描画で画面が止まらないかの比較に使い、計算の時間としては扱わないでください。証明書の1,000行・10,000行と正規表現の1,000行は、結果の表示までの時間です（PEM のブロック数の上限64は、このコミットの後で追加したため、現在のスクリプトでは証明書の10,000行も上限エラーになります）。

新しく計測したら、`<対象>-YYYY-MM-DD.json`（例：`epoch-parsing-2026-11-12.json`。複数の画面をまとめて測ったときの対象は `performance`）の名前で保存し、この表に追加してください。同じ日の変更前後や形式違いの記録は、末尾に `-before`・`-after`・`-traced` などを付けて分けます。測定日が分からない過去の記録は、日付の代わりに `undated` を付けています。

## サブネットの集約・重複チェック

現行ビルドで同じ種類の入力を測るコマンドは [計測手順](../PERFORMANCE.md#サブネットの集約重複チェック) にあります。

2026年11月9日、コミット `3ecf935` の本番ビルドと、同じコミットに修正を加えた本番ビルドを比較しました。環境は Windows、Core i7-1165G7、Node v24.22.1、Chromium 156.0.8078.4 です。重複も隣接もしない合成IPv4アドレス10万件を使い、重複チェックの入力には各行に `/32` を付けました。各ケースは新しいページで3回実行しました。

| 対象 | 完了時間の中央値（前 → 後） | 最大描画間隔の中央値（前 → 後） | 修正後の Worker 内計算／結果の受信まで／受信後2フレーム |
|---|---:|---:|---:|
| 集約 | 1,217 → 533 ms | 1,200 → 117 ms | 255／1.7／29 ms |
| 重複チェック | 333 → 450 ms | 317 → 100 ms | 201／0.3／22 ms |

入力を更新したフレームから、結果を検出した次のフレームまでを完了時間とし、その間の最大 `requestAnimationFrame` 間隔も記録しました。修正前の計算時間は同期処理の開始から IPv4・IPv6 の結果を合成する直前までです。修正後の計算時間は Worker の要求受信から応答送信直前までで、結果の合成を含みます。結果の受信までは応答送信直前からメインスレッドでの受信までで、メッセージの待ち時間も含みます。完了時間には Worker 起動前の150 msの待機も含まれます。

集約の表示は1,511,791単位から50,000単位に減り、コピーは全文を保持します。重複チェックは完了までの時間が延びる一方、描画が止まる時間が短くなりました。

## 過去の計測環境と結果

ここからは SQL 整形を提供していた時点の記録です（SQL整形は現在提供していません）。JSON・SQL整形と文字数・バイト数を対象に、改善前後の本番ビルドを同じ合成データで比較しました。測定日・対象コミットSHAは元の記録にないため未記録です。SQL は同じ要素数の `IN (12345,12345,...)` で長い1行の処理を検査しました。現在のスクリプトではこのケースを実行しません。

環境は Windows、Intel Core i7-1165G7、Node v24.22.1、Chromium 156.0.8078.4。各ケース1回の観測値で、性能を保証する値ではありません。改善前はツールごとの入力保存を導入した後、計算のWorker分離とプレビュー制限を加える前のビルドです。

### 結果

単位はミリ秒です。生データは [改善前](performance-undated-before.json)・[改善後](performance-undated-after.json) にあります。

| ツール | 件数／行数 | 完了：改善前 | 完了：改善後 | 最大描画間隔：改善前 | 最大描画間隔：改善後 |
|---|---:|---:|---:|---:|---:|
| JSON | 1,000 | 126 | 240 | 50 | 17 |
| JSON | 10,000 | 833 | 291 | 733 | 50 |
| JSON | 100,000 | 7,146 | 871 | 6,650 | 250 |
| SQL | 1,000 | 63 | 227 | 17 | 17 |
| SQL | 10,000 | 128 | 245 | 67 | 33 |
| SQL | 100,000 | 18,983 | 304 | 18,883 | 17 |
| 文字数 | 1,000 | 262 | 310 | 183 | 67 |
| 文字数 | 10,000 | 512 | 294 | 417 | 83 |
| 文字数 | 100,000 | 2,421 | 661 | 2,267 | 250 |

小さい入力では、150msの待機とWorker起動の分だけ完了が遅くなる場合があります。大きな入力では処理完了と画面の応答性の両方が改善しました。5.2百万単位のJSON入力や約110万単位のテキストでも、入力転送・保存などによる250msの描画間隔は残っており、すべての端末で無停止になるわけではありません。

### 当時の変更内容

- JSON・SQL整形と文字数計算を専用Workerへ移動。入力変更・画面移動・手動中断でWorkerを終了し、古い結果は表示しません。10秒で打ち切り、同じ入力を再計算できます。
- SQLのトークン追加時の `line.trim()` を除去。長いIN句で、成長中の行全体を何度も走査していた処理をなくしました。
- 入力と整形結果の表示は50,000 UTF-16単位まで。計算・コピーボタン・ファイル保存には元の全文を渡します。大きな入力の直接編集は、利用者が「全文を編集」で選択できます。
- 文字数は表示外を含む全行を計測し、100行ずつ表示。1行の表示は1,000単位、注意文字の一覧は各100種類までに制限し、計測値は切り詰めません。文字コードの強調表示もWorkerで作ります。
- 入力は800万単位、JSON・SQLの整形出力は2,000万単位まで。深い入れ子による出力の際限ない増加を抑えます。大量のJSON警告は先頭5件と残件数だけを画面へ渡します。
- 当時は計算Worker専用のTrusted Typesポリシーを追加し、固定URLを検査していました。現在はページのCSPをWorkerへ引き継ぐため、ビルドに含まれるWorkerのコードから作った `blob:` URLだけを許可します（`src/lib/createTrustedWorker.ts`）。
