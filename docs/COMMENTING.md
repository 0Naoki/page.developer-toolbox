# ソースコードコメント（TSDoc）

TypeScript・TSX の説明コメントは、日本語の TSDoc 形式（`/** ... */`）で書きます。アプリだけでなく、テストとビルド設定も対象です。JavaScript の説明コメントも同じ書式にそろえます。CSS・PowerShell・YAML などには、それぞれの言語のコメント構文を使います。

## 宣言の説明

関数・型・定数・プロパティの説明は、その宣言の直前に置きます。最初に役割を短く書き、実装の理由や制約は `@remarks` に分けます。単純な説明は `/** 日本時間の今日の日付。 */` のような1行でも構いません。

引数の単位・範囲・既定値、戻り値の `null` や状態の意味など、型だけでは伝わらない契約を記載してください。型の情報を `{string}` のように重複して書く JSDoc 記法は使いません。

```ts
/**
 * UNIX 時刻から日本時間の日付を求める。
 *
 * @param now - ミリ秒単位の UNIX 時刻。省略時は現在時刻。
 * @returns 日本時間の年月日。
 */
```

必要なタグだけを使います。関数ごとに同じ説明を機械的に繰り返す必要はありません。

| タグ | 書く内容 |
|---|---|
| `@remarks` | 処理の理由、前提、制約、副作用、保存・通信の有無 |
| `@param name - 説明` | 引数の意味・単位・許容範囲 |
| `@typeParam T - 説明` | ジェネリック型の制約や用途 |
| `@returns` | 戻り値の意味、未検証・不一致・未対応などの違い |
| `@throws` | 呼び出し側で扱うべき例外と発生条件 |
| `@example` | 入出力や呼び出し例。コードはフェンスで囲む |

コード中の識別子・HTML・JSON・正規表現などはバッククォートで囲み、説明中の記号が TSDoc のタグや HTML として解釈されないようにします。

## 実装の補足とテスト

処理の途中に必要な補足も `/** ... */` を使います。処理を読み上げる説明ではなく、「なぜ必要か」「どの不具合を防ぐか」を書きます。これらは宣言の API ドキュメントとは区別し、意味のない `@param` などは付けません。JSX 内は `{/** 説明 */}` と書きます。

テストでは、回帰させたくない入力やブラウザ固有の制約を説明します。元になった不具合の経緯が長い場合は、ドキュメントに置いてリンクします。

ツールやコンパイラが要求する指示コメントは、指定された構文を保ちます。たとえば三重スラッシュ参照や最適化指示を、説明コメントへの統一のために書き換えてはいけません。

## 更新するときの確認

- 実装と同時に、関連するコメント・利用ガイド・テスト手順を更新する。
- 入力の保存、署名検証、境界値、時間やサイズの単位は、実装に照らして確認する。
- 過去の計測記録は計測時点を明記し、現在の仕様や性能保証と混同させない。
- コメントだけの変更でも `npm run check` を実行し、構文や型に影響がないことを確認する。

実行手順は [TESTING.md](TESTING.md)、コードの配置は [ARCHITECTURE.md](ARCHITECTURE.md) を参照してください。
